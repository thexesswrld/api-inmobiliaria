00 · Vista completa

Mapa general del ciclo de venta

El camino normal va de izquierda a derecha. El pago se repite por cada cuota. Desde una venta separada o vigente se puede salir por anulación o resolución, y la unidad vuelve a quedar disponible.

  A["01 Cotizar<br/>Asesor + Cliente<br/>solo consulta"] --> B["02 Separar unidad<br/>venta SEPARADA<br/>unidad SEPARADO"]
  B --> C["03 Pago de separación<br/>Caja"]
  C --> D["04 Validar pago<br/>Administración"]
  D --> E["05 Comprobante<br/>boleta o factura"]
  B --> F["06 Formalizar contrato<br/>venta VIGENTE<br/>unidad VENDIDO<br/>cronograma"]
  F --> G["03 a 05 Pago de cuotas<br/>se repite cada mes"]
  G --> G
  G --> H["07 Cancelar<br/>saldo 0, venta CANCELADA<br/>cliente es propietario"]
  H --> I["07 Entregar<br/>venta ENTREGADA<br/>unidad ENTREGADO"]
  B -. desiste .-> X["07 Anular o resolver<br/>unidad DISPONIBLE"]
  F -. incumple .-> X
  J["08 Job diario"] -. marca VENCIDA .-> G
01 · Solo lectura

Cotizar

El cliente pide precios. El asesor recorre proyecto, sectores y unidades disponibles, muestra el plano con las zonas clicables y simula el cronograma. Nada se guarda: no hay transacción.

sequenceDiagram
  autonumber
  actor C as Cliente
  actor AS as Asesor
  participant API
  participant BD as Base de datos
  C->>AS: Pide cotizar un lote o departamento
  AS->>API: GET /proyectos
  API->>BD: SELECT pro_proyecto activos
  API-->>AS: Lista de proyectos
  AS->>API: GET /proyectos/:id/sectores
  API->>BD: SELECT pro_sector en árbol
  API-->>AS: Etapas, manzanas, torres, pisos
  AS->>API: GET /unidades?sector=12&estado=DISPONIBLE
  API->>BD: SELECT pro_unidad con estado_comercial
  API-->>AS: Unidades con precio, áreas y atributos
  AS->>API: GET /proyectos/:id/modelos
  API->>BD: SELECT pro_modelo y pro_modelo_referencia
  API-->>AS: Plano o render con zonas clicables por unidad
  AS->>API: POST /cotizaciones/simular
  Note over API: logic de cronograma<br/>precio - descuento, inicial, financiado, cuotas<br/>no escribe en la BD
  API-->>AS: Cronograma simulado
  AS-->>C: Entrega la cotización

02 · Transacción

Separar la unidad

El cliente elige la unidad. Se crea la venta en estado SEPARADA con sus unidades y la cuota de separación. La base de datos bloquea la unidad y la pasa a SEPARADO sola, dentro de la misma transacción.

sequenceDiagram
  autonumber
  actor C as Cliente
  actor AS as Asesor
  participant API
  participant BD as Base de datos
  C->>AS: Elige la unidad y acepta separarla
  AS->>API: POST /ventas con cliente, unidades y monto de separación
  Note over API: Valida el DTO con zod<br/>Permiso ven.venta.separar
  critical prisma.$transaction
    API->>BD: INSERT ven_venta, estado_comercial SEPARADA
    API->>BD: INSERT ven_detalle_venta, una fila por unidad
    Note over BD: trigger trg_detalle_venta_sync<br/>fn_sincronizar_unidades_venta
    BD->>BD: Bloquea la unidad con FOR UPDATE
    BD->>BD: ¿Otra venta activa la ocupa? ¿Está BLOQUEADA?
    BD->>BD: UPDATE pro_unidad a SEPARADO
    API->>BD: INSERT ven_cuota tipo SEPARACION, PENDIENTE
  option La unidad ya está comprometida o bloqueada
    BD-->>API: RAISE EXCEPTION, se revierte todo
    API-->>AS: 422 REGLA_NEGOCIO con el mensaje
  end
  API-->>AS: 201 venta SEPARADA y su cuota de separación
  AS-->>C: Constancia de separación

Concurrencia
Si dos asesores separan la misma unidad a la vez, el bloqueo los atiende en fila: el segundo recibe el error de unidad comprometida.
03 · Transacción

Registrar un pago

Caja registra el dinero recibido y lo reparte entre una o varias cuotas, a capital o a mora. La base de datos valida los topes y recalcula cada cuota.

sequenceDiagram
  autonumber
  actor C as Cliente
  actor CJ as Caja
  participant API
  participant BD as Base de datos
  C->>CJ: Paga en efectivo, transferencia o Yape
  CJ->>API: POST /ventas/:id/pagos con monto, medio y reparto por cuota
  critical prisma.$transaction
    API->>BD: INSERT ven_pago, estado_pago REGISTRADO
    Note over BD: trg_pago_validar<br/>otra moneda exige tipo_cambio
    API->>BD: INSERT ven_pago_aplicacion por cada cuota, CAPITAL o MORA
    Note over BD: trg_aplicacion_llenar_venta<br/>trg_pago_aplicacion_cuota
    BD->>BD: Bloquea el pago y suma lo aplicado
    BD->>BD: fn_recalcular_monto_pagado de cada cuota
    BD->>BD: UPDATE ven_cuota monto_pagado y estado
  option Se reparte más de lo pagado o más de lo que vale la cuota
    BD-->>API: RAISE EXCEPTION, se revierte todo
    API-->>CJ: 422 REGLA_NEGOCIO
  end
  API-->>CJ: 201 pago REGISTRADO y cuotas actualizadas
  CJ-->>C: Constancia de pago

Escribe
ven_pago, ven_pago_aplicacion. ven_cuota la actualiza el trigger

Errores
  • El pago está en otra moneda que la venta: tipo_cambio es obligatorio
  • El pago 88 es de 500.00 y se estarían aplicando 650.00
  • La cuota 3 de la venta 12 vale 1200.00 y se le estaría aplicando 1500.00 a capital
  • La cuota 3 de la venta 12 está ANULADA y no puede recibir pagos
Nota
La cuota cuenta pagos REGISTRADO y VALIDADO. El IGV no va aquí: va en el comprobante.
04 · Transacción

Validar, rechazar o anular un pago

Administración confirma que el dinero llegó, o lo rechaza o anula con un motivo. Si el pago deja de contar, sus cuotas se recalculan solas.

sequenceDiagram
  autonumber
  actor AD as Administración
  participant API
  participant BD as Base de datos
  AD->>API: PATCH /pagos/:id/estado con VALIDADO, RECHAZADO o ANULADO
  critical prisma.$transaction
    API->>BD: UPDATE ven_pago estado_pago y motivo_anulacion
    Note over BD: trg_pago_validar<br/>RECHAZADO o ANULADO exige motivo<br/>un pago ANULADO no se reactiva
    Note over BD: trg_pago_estado
    BD->>BD: fn_recalcular_monto_pagado de cada cuota del pago
    BD->>BD: Si se anuló, la cuota vuelve a PENDIENTE, PAGO_PARCIAL o VENCIDA
  option Falta motivo o se intenta reactivar
    BD-->>API: RAISE EXCEPTION
    API-->>AD: 422 REGLA_NEGOCIO
  end
  API-->>AD: Pago con su nuevo estado

ven.pago.validar, ven.pago.anular

  • El pago 88 ya fue procesado: no se elimina, se anula con motivo
05 · Transacción + envío aparte

Emitir el comprobante

Por cada pago se emite una boleta (03) o factura (01). El número sale de la serie de forma segura, y una vez emitido el comprobante no se modifica: solo se anula o se corrige con nota de crédito.

sequenceDiagram
  autonumber
  actor AD as Administración
  participant API
  participant BD as Base de datos
  participant S as SUNAT u OSE
  AD->>API: POST /pagos/:id/comprobante con tipo y serie
  Note over API: Calcula op_gravada, IGV 18 por ciento y total<br/>copia documento, nombre y dirección del cliente
  critical prisma.$transaction
    API->>BD: SELECT fn_siguiente_numero_comprobante del id_serie
    Note over BD: Bloquea ven_serie<br/>nunca se repite un número
    BD-->>API: 124
    API->>BD: INSERT ven_comprobante EMITIDO, SUNAT PENDIENTE
  end
  API-->>AD: Comprobante B001-00000124
  API->>S: Envía el XML firmado, proceso aparte
  S-->>API: CDR con ACEPTADO, OBSERVADO o RECHAZADO
  API->>BD: UPDATE estado_sunat, hash_cpe, url_xml, url_cdr
  Note over BD: trg_comprobante_inmutable<br/>solo cambian estado, datos SUNAT y archivos

06 · Transacción

Formalizar el contrato

Con la separación pagada, se fijan precio final, inicial y número de cuotas. La venta pasa a VIGENTE, la unidad a VENDIDO y se crea el cronograma.

sequenceDiagram
  autonumber
  actor C as Cliente
  actor JV as Jefe de ventas
  participant API
  participant BD as Base de datos
  C->>JV: Firma el contrato
  JV->>API: PATCH /ventas/:id/formalizar con precio, descuento, inicial y cuotas
  Note over API: logic de cronograma<br/>monto_final = bruto - descuento<br/>financiado = final - inicial
  critical prisma.$transaction
    API->>BD: UPDATE ven_venta montos y estado_comercial VIGENTE
    Note over BD: trigger trg_venta_unidades
    BD->>BD: UPDATE pro_unidad a VENDIDO
    API->>BD: INSERT ven_cuota INICIAL y MENSUAL 1 a n, PENDIENTE
  option Montos que no cuadran
    BD-->>API: CHECK ck_venta_monto_final
    API-->>JV: 422 REGLA_NEGOCIO
  end
  API-->>JV: Contrato VIGENTE con su cronograma
  Note over API,BD: Control: v_venta_resumen<br/>diferencia_inicial y diferencia_cronograma deben ser 0

07 · Transacción

Cancelar, entregar, anular o resolver

Todos son un cambio de estado de la venta. El trigger lleva el estado a las unidades. Marcar CANCELADA lo decide la API después de revisar que el saldo sea 0.

sequenceDiagram
  autonumber
  actor AD as Administración
  participant API
  participant BD as Base de datos
  AD->>API: PATCH /ventas/:id/estado con CANCELADA
  API->>BD: SELECT saldo de v_venta_resumen
  alt saldo mayor a 0
    API-->>AD: 422 la venta tiene saldo pendiente
  else saldo igual a 0
    API->>BD: UPDATE ven_venta a CANCELADA
    Note over BD: trg_venta_unidades
    BD->>BD: Unidad VENDIDO, id_propietario = cliente
    API-->>AD: Venta CANCELADA
  end
  AD->>API: PATCH /ventas/:id/estado con ENTREGADA
  API->>BD: UPDATE ven_venta a ENTREGADA
  BD->>BD: Unidad ENTREGADO
  AD->>API: PATCH /ventas/:id/estado con ANULADA o RESUELTA
  critical prisma.$transaction
    API->>BD: UPDATE ven_venta a ANULADA o RESUELTA
    BD->>BD: fn_liberar_unidad: DISPONIBLE, sin propietario
    API->>BD: UPDATE ven_cuota pendientes a ANULADA
  end
  API-->>AD: Venta cerrada y unidad liberada

Ojo
Una unidad BLOQUEADO no se libera sola. Las cuotas pendientes no se anulan por trigger: lo hace la API.
08 · Tarea programada

Marcar cuotas vencidas

Una vez al día, las cuotas impagas con fecha pasada pasan a VENCIDA. No lo inicia ninguna persona: lo dispara un job.

  BD-->>J: Cantidad de cuotas marcadas

Por decidir

Lo que la base de datos todavía no resuelve

Estos puntos salen de leer los triggers: la base de datos no los hace sola, así que la API o una decisión del negocio tiene que cubrirlos.

Las cotizaciones no se guardan

No hay tabla de cotizaciones. Si quieren historial o seguimiento de prospectos, falta una tabla tipo ven_cotizacion.

Pasar a CANCELADA no es automático

Ningún trigger cambia la venta cuando se paga todo. La API debe revisar saldo = 0 en v_venta_resumen, ya sea al validar el último pago o con una acción manual.

Anular una venta no anula sus cuotas

El trigger libera la unidad, pero las cuotas pendientes siguen igual. La API debe pasarlas a ANULADA en la misma transacción.

El job de cuotas vencidas no está programado

fn_marcar_cuotas_vencidas() existe, pero alguien tiene que llamarla cada día: @nestjs/schedule o pg_cron.

El envío a SUNAT es externo

La base de datos guarda el estado y los archivos, pero el XML, la firma y el envío los hace la API con un OSE o proveedor de facturación.

¿Quién calcula la mora?

Existe monto_mora en la cuota, pero ningún trigger la calcula. Hay que definir la regla (porcentaje diario, monto fijo) y dónde vive.
